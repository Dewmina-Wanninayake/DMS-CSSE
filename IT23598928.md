### 3.4 Git
- **Branches:** `main` (protected, always green) ← `feat/<uc-id>-<short>` e.g. `feat/da-001-trend-analysis`; `fix/…`, `chore/…`, `docs/…`, `test/…`. Foundation: `chore/foundation`.
- **Commits:** Conventional Commits — `feat(policy-analytics): add risk classifier`. Types: feat, fix, test, docs, refactor, chore, style. One logical change per commit; imperative mood.
- **Pull requests:** ≤ ~400 changed lines where possible; template must state: use case + steps/extension IDs covered, critique findings addressed, screenshots vs hi-fi, tests added + coverage, new env vars/migrations. Needs **1 approval from a member other than the author** (Member 1 reviews Member 2 and vice-versa; Member 3 ↔ Member 4). CI (lint + typecheck + test) must pass. Squash-merge.

### 3.5 Formatting and linting
Prettier (single quotes, semicolons, 100 cols, trailing commas `all`, 2-space indent, LF). ESLint: `@typescript-eslint/recommended`, `no-console` (use the logger), `eqeqeq`, `no-unused-vars` as error, React hooks rules. `npm run lint`, `npm run format:check`, `npm run typecheck`, `npm test` must pass locally before a PR.

### 3.6 API standard
- **Envelope** (all endpoints):
  ```json
  { "success": true,  "data": { }, "meta": { "page": 1, "pageSize": 20, "total": 3 } }
  { "success": false, "error": { "code": "VALIDATION_ERROR", "message": "…", "details": [ { "field": "…", "message": "…" } ] } }
  ```
- **Status codes:** 200 OK · 201 Created (+ `Location`) · 204 No Content · 400 malformed request · 401 unauthenticated · 403 wrong role · 404 not found · 409 conflict / invalid state transition / stale data · 422 semantic validation failure (e.g. regulatory conflict, insufficient stock) · 500 unexpected (message never leaks internals).
- **Error codes** are `UPPER_SNAKE` strings from `@dms/shared` (`VALIDATION_ERROR`, `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `INVALID_STATE_TRANSITION`, `INSUFFICIENT_DATA`, `REGULATORY_CONFLICT`, …). Modules add module-specific codes to their own file, never reuse a code for a different meaning.
- Pagination: `?page=1&pageSize=20` (max 100). Dates: ISO-8601 UTC strings; business dates (`YYYY-MM-DD`) are evaluated in `APP_TIMEZONE` (default Asia/Colombo), never in server UTC. Ids: integer for DB rows, exposed as numbers.
- API contract for every module is written in `docs/api/<module>.md` and agreed in a PR **before** implementation (§6).

### 3.7 Validation
Server is authoritative: every body/query/param is parsed by a `zod` schema through the shared `validate()` middleware. Client validates for UX using the same constants (limits live in `@dms/shared`), never as the only check. Field messages are human-readable sentences.

### 3.8 Error handling
Throw typed `AppError` subclasses from services; a single error middleware maps them to the envelope. No `try/catch` that swallows errors; no `console.log`. Client: the shared `apiClient` converts envelope errors into `ApiError`; pages render `ErrorState` (with retry) — never a blank screen.

### 3.9 Loading / empty / error states (mandatory on every data view)
`LoadingState` (spinner + label, `aria-busy`), `EmptyState` (icon + one-line explanation + next action), `ErrorState` (message + Retry), `OfflineBanner` for Pending-sync/stale data (critique Interaction #3). A page is not done until all four are reachable and tested.

### 3.10 Authentication / authorisation (foundation, not graded — S6)
`Authorization: Bearer <JWT>`; payload `{ sub, role }`. `requireAuth` then `requireRole(...roles)` on every route (deny by default; the registry refuses to mount a router whose routes lack a guard in tests). Roles are the `Role` enum in `@dms/shared`. The client reads the session from the foundation `AuthContext` and filters navigation by role; the server is the real enforcement.

### 3.11 Security
Parameterised SQL only (prepared statements); zod on all input; `helmet`; CORS limited to `CLIENT_ORIGIN`; secrets only in `.env` (never committed; `.env.example` lists every variable); scrypt password hashes; generic login errors; request body size limit; no stack traces in responses; output rendered by React (no `dangerouslySetInnerHTML`).

### 3.12 Shared constants and environment variables
Domain constants (enum values, field limits, thresholds' *defaults*) live in `shared/src`. Tunables that operators change (risk thresholds, retry intervals) live in DB settings or env — **no magic numbers in components or services**. `.env.example` is the single list of variables; a new variable is added in the same PR that uses it.

### 3.13 Responsive design / accessibility / UI consistency
Desktop-first; breakpoints 640 / 768 / 1024 / 1280 px. ≥ 1024 sidebar nav, below 1024 header + bottom tabs (matches hi-fi). Min touch target 44 px on mobile. Labels associated with inputs; focus ring always visible; colour never the only signal (badges include text); contrast ≥ 4.5:1 for text (critique Interaction #4); `aria-live` for toasts/errors; keyboard operable dialogs. **No member writes a button, card, input, badge, alert, modal or step bar themselves** — they use `client/src/shared/ui`. A missing primitive is added to shared via a small PR first.

### 3.14 Reusable code / avoiding duplication
Rule of three: if a second member needs it, move it to `shared/`. Format helpers, API client, hooks (`useAsync`, `useOnlineStatus`), enums, validation limits, ID/date helpers are shared only. PRs touching `shared/` or `core/` need review from the foundation owner.

### 3.15 Comments and documentation
Self-explanatory names first; comments explain **why** (a rule from the critique, an assumption), cite the finding (`// DA #4: testable rule …`). Every public service method has a short TSDoc. Each module delivers `docs/modules/<uc-id>.md` and `docs/api/<module>.md`.

### 3.16 Design patterns expected (rubric: "appropriate design patterns applied correctly")
Repository (data access), Strategy (rules that vary: risk classification, notification channels, simulation models), State/State-machine (statuses with allowed transitions: policy, team, report), Adapter (external feeds: hydromet provider, notification gateway), Factory/DI via constructor injection (composition root per module). Apply a pattern only where it removes a real conditional or coupling.

### 3.17 Testing conventions
- Vitest; test file beside its unit; `describe(unit) → it('should … when …')`; Arrange-Act-Assert; one behaviour per test.
- Every module covers positive, negative, edge and error cases for **each scenario step and extension** (name tests with the step id: `it('3a: returns sparse-data warning …')`).
- Server: domain = pure unit tests; services = against in-memory SQLite with real migrations (no DB mocks); routes = Supertest (status code, envelope, auth/role). Client: components/hooks/pages with Testing Library; network mocked at the `apiClient` boundary only.
- Coverage threshold **80 % lines/functions/branches/statements on the module's own folders**, enforced in `vitest.config`. Do not write assertion-free tests to inflate coverage.

## 6. Integration strategy

1. **Foundation first.** Member 2 authors it (it is code-ready before the others have started), **Member 1 as repository owner reviews and merges it** to `main`. Until it is merged, others write only their `docs/api/*.md`.
2. **Branches.** Every member branches from the latest `main` after Phase 0; `feat/<uc-id>-…`. Rebase on `main` daily; never merge another feature branch into yours.
3. **Isolation.** You edit only: your `server/src/modules/<m>/`, `client/src/modules/<m>/`, your `docs/` files, your migration range, and **one line each** in `server/src/modules/registry.ts` and `client/src/app/moduleRegistry.ts`. Anything else (shared/core/shared UI/tokens) needs a separate small PR labelled `shared`.
4. **Shared components.** Check `client/src/shared/ui` before building. Need a new one → separate `shared` PR → reviewed by the foundation author → rebase. No local copies, ever.
5. **API contracts.** Written first in `docs/api/<module>.md` (path, method, role, request/response schemas, error codes). Cross-module calls (e.g. `GET /policies/active/warning-criteria`) are listed in the *provider's* contract and consumed by the other side only through the typed client in `@dms/shared`.
6. **Database changes.** Own tables only, in your numeric migration range; shared tables (`users`, `districts`, `hazard_reports`, `notifications`, `hydromet_observations`) are changed only by a `shared` PR with an additive migration (new nullable column / new table). Never edit an applied migration — add a new one. Seeds are idempotent.
7. **Reviews.** Pairs: M1 ↔ M2, M3 ↔ M4. Reviewer checks: scenario/extension coverage against the revised scenario, critique-finding traceability, hi-fi match, states, tests meaningful, no duplicated UI, lint/typecheck/test green.
8. **Conflicts.** The two registry files are the only expected conflicts: keep **both** lines. Any other conflict means someone touched a file they do not own — stop and ask the owner. Migration number clash ⇒ you left your range.
9. **Test together.** `npm test` at root runs all workspaces; `npm run test:coverage` per module path. Before Phase 7: seed DB (`npm run db:seed`), run `npm run dev`, execute the cross-module script in `docs/integration-checklist.md` (create → verify → analyse → publish → warning-criteria visible; shelters visible read-only).
10. **Final verification** against the hi-fi and rubric: for each module open the Group 03 page and the running screen side by side (differences must be explained by C1–C13 or a critique finding); tick every scenario step/extension; confirm coverage report ≥ 80 %; confirm `docs/modules/<uc-id>.md` is complete.

## 8. Definition of Done (every member)

A module is **done** only when **all** of these are true:

1. **Functional:** every main-scenario step and every extension in the revised scenario (critique §11.4) works end-to-end in the running app — checked off in `docs/modules/<uc-id>.md` against step ids.
2. **Critique traceability:** each finding listed for the module has a visible implementation or an explicit "out of scope" decision from the critique.
3. **High-fidelity match:** each screen compared side by side with its Group 03 page; differences are only those in C1–C13 or the critique's §11.5 list.
4. **Backend/API:** endpoints match `docs/api/<module>.md`; envelope + status codes per §3.6.
5. **Database:** migrations in the owner's range apply on a clean DB and on top of the others; seed idempotent; no raw SQL outside repositories.
6. **Validation:** server-side zod on all inputs; client messages; boundary values tested.
7. **Error handling:** typed errors; no uncaught promise/500 on bad input; no console output.
8. **States:** loading, empty, error and offline/stale states exist for every data view and are tested.
9. **Auth:** every route guarded; role matrix tested (allowed + forbidden + unauthenticated).
10. **Responsive & a11y:** usable at 360 px and 1280 px; keyboard path; labels; focus; contrast ≥ 4.5:1.
11. **Tests:** module coverage ≥ 80 % (lines, functions, branches, statements); positive/negative/edge/error present; assertions meaningful; suite green.
12. **Code quality:** `lint`, `format:check`, `typecheck`, `build` clean; layered architecture; named patterns used where §3.16 says; no duplicated UI; no magic numbers.
13. **Docs:** TSDoc on public services; `docs/api/<module>.md`; `docs/modules/<uc-id>.md` (files, components, APIs, tables, env vars, assumptions, remaining work).
14. **Git/PR:** conventional commits; PR reviewed by the counterpart; CI green; squash-merged; branch deleted.
15. **Rubric coverage:** implementation accuracy (alignment with scenarios/sequence diagram, UX, enhancements integrated) · code quality · unit testing — each ticked in the PR description.
